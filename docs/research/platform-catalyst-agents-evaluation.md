## 0. Executive summary

`platform-catalyst` is a **sibling fork** authored by the same engineer (BSD-3-Clause, copyright `BittahCriminal`, `https://github.com/BittahCriminal/platform-catalyst`) that targets the **same Senior Platform Engineer challenge** with the **same Honda Construct framing** and the **same five-level construct hierarchy** that Catalyst encodes in ADR-002. It is functionally a **superset** of the current Catalyst repo: 12 agent personas, 48 skills, a `catalyst-judge` MCP server, and a deeper docs scaffold (`PLAN.md`, `CLAUDE.md`, `DECISIONS.md`, `RUNBOOK.md`, `THREAT-MODEL.md`, `KAIZEN.md`).

Catalyst (`Cloud-Byte-Consulting/Catalyst`) is the **leaner, in-flight rewrite** on the same ideas: ADR-001 (GitHub Issues state machine), ADR-002 (construct hierarchy), ADR-003 (static + ephemeral envs), ADR-004 (RLM). This report was written as a pre-import snapshot; several statements below are historical and have since been superseded by the stacked PR chain (#24/#26/#28/#30/#31).

**Headline recommendations**:

1. **Import 7 of 12 agents** as-is or with light fork (the ones that map cleanly to the rubric weights and to existing ADRs).
2. **Adapt 2 agents** (`platform-engineering-architect`, `automation-architect`) to remove dead references (`PLAN.md`, `CLAUDE.md`, `DECISIONS.md`) and re-anchor to the Catalyst ADR set.
3. **Defer 1 agent** (`intent-judge`) until the plugin it depends on exists (`catalyst-judge` plugin not vendored).
4. **Reject 1 agent** (`docs-communicator`) only as a copy — its content overlaps with the in-flight worker on issue #19 + Communication & Documentation milestone work; merge the useful parts instead.
5. **Coordinate with the in-flight `rc/aws-agentic-platform-engineering` branch** (issue #19) **before** importing — that branch is explicitly creating `.cursor/agents/aws-platform-engineer.md`, `.cursor/rules/aws-platform-engineering.mdc`, `.cursor/skills/aws-platform-engineering/`, and 5 new prompt files. Without coordination there is a high risk of two overlapping AWS-platform personas landing in this repo.

## Decisions made

The following questions from § 7 have been resolved. Each answer is binding for the implementation work.

1. **Branch coordination** — Option (a) chosen: pause the platform-catalyst agent import until PR #20 (`rc/aws-agentic-platform-engineering` → `release`) is merged. The work then proceeded as a stacked branch chain rather than a single `rc/import-pc-agents` branch.
2. **AWS-platform persona split** — Two personas chosen for the AWS-platform space:
  - `platform-engineering-architect` — strategy-level, cross-cutting IDP / org / landing-zone decisions.
  - `aws-platform-engineer` — AWS implementation detail (already being added by `rc/aws-agentic-platform-engineering` / PR #20).
  - `security-hardener` will be imported as a **separate, third security persona** — not merged into either of the above.
3. `**intent-judge` direction** — Option (c) chosen: re-implement as a **lightweight Cursor rule + thin MCP shim (~80 lines)**. Do **not** vendor the full `plugins/catalyst-judge/` package.
4. **IaC standard** — **Terraform stays.** No CDK, no Pulumi for this project.
5. **Dapr** — Excluded from the import. No Dapr adoption planned. The `dapr-expert` agent is dropped.
6. **Skill import strategy** — Phased lockstep confirmed:
  - Phase 1: 7 skills
  - Phase 2: 12 skills
  - Phase 3: 9 skills
   Do **not** import all 30+ skills at once.
7. `**docs-communicator` boundary + `score-expert` import path** — Merge `docs-communicator` into `platform-engineering-architect` (do not import it as a standalone agent). Import `score-expert` as-is.
8. **Books library** — Keep book citations as-is. No `docs/research/agent-references.md` extraction required; citations remain in the agent files and are governed by the existing `AGENTS.md` guidance on personal reference files.
9. **License / attribution shape** — Keep as-is (single attribution approach in `AGENTS.md` + per-file `Vendored from` comment, consistent with the RLM toolkit precedent). No separate `NOTICE` file required.
10. **Agent phase groupings (`cicd-operator` fork target; `automation-architect` ECS vs Lambda scope)** — Curate before importing. Do **not** import either agent until their scope is confirmed against Catalyst's chosen runtime. The ECS Fargate decision is expected from the completion plan; import of these two agents is blocked on that outcome.
11. `**ai-reviewer-architect` Bedrock model binding** — Implement the model-binding as a **separate MCP server** (not inline in the agent file). The agent file itself should not pin Bedrock model IDs; the MCP server is the canonical binding point.
12. **ADR numbering drift (ADR-001 / ADR-002 canonical lock)** — Lock confirmed: ADR-001 and ADR-002 are the canonical identifiers in Catalyst. A search/replace pass on any imported agent files that reference ADR-008 / ADR-009 will be performed at import time.
13. **4-phase agent landing sequence** — The import proceeds in four phases as stacked PRs (#24 -> #26 -> #28 -> #30), with `rc/intent-judge-shim` as the final stacked branch (#31).
  - **Phase 1** — `terraform-engineer`, `checkov-expert`, `opa-expert` (IaC + policy foundation; all import-as-is; lowest coordination risk).
    - **Phase 2** — `automation-architect`, `cicd-operator`, `security-hardener` (Automation Service + CI/CD + Security rubric areas).
    - **Phase 3** — `ai-reviewer-architect`, `score-expert` (AI-native + Score portability tier).
    - **Phase 4** — `platform-engineering-architect` (architect tier; sequenced after #20 resolves the persona-overlap question per decision #2).
14. **Canonical target paths and filenames** — All imported agents land in `Catalyst/.cursor/agents/` preserving the original source filenames (no renaming). The §5.6 summary tree in this report is the binding reference. Only the ~30 dependent skills listed in §5.6 are imported in lockstep; the remaining 18 skills (belonging to deferred agents or out-of-scope) are not brought in.
15. **New `catalyst-agents.mdc` Cursor rule** — A new `.cursor/rules/catalyst-agents.mdc` is to be created alongside the Phase 1 import. It auto-routes Cursor sessions to the correct persona by description match (the rule does not alter any agent file content).
16. **RLM long-context annotation on import** — On import, prepend a one-line "Long-context handling" bullet to each agent's "Required behavior" block: *"If the artifact exceeds ~50k chars, follow `.cursor/rules/rlm-workflow.mdc` before reading inline."* This closes the ADR-004 alignment gap noted in §4.3 and §6 (RLM divergence risk).
